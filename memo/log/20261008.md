## データの取り込みを、利用者と管理者で分ける
- 方針：利用者が入れるもの（自分のタイムライン・Google Takeout）は取り込み画面の「ファイルを選ぶ」で送る。管理者が入れるもの（位置参照情報・OpenStreetMap）は、画面ではなく管理者向けの文書（`deploy/README.md`）に書く
- Google Takeout を画面から送れるようにした（`POST /api/takeout`。multipart/form-data で zip を複数まとめて、上限 200MB）。zip は `data/users/<利用者名>/takeout/` に置き換えて残し、入れたあとすぐ地点への割り当ても行う
- 「ファイルを選ぶ」を複数選択にし、.zip は Takeout、それ以外はタイムラインとして送る。「共有」でも zip を受け取る
- 取り込み画面から、サーバーのコマンドの説明を外し、「サーバーの管理者が入れます（管理者向けの説明：設置手順）」とリンクを出す。保存リストのタブの案内も同様に直した
- 確かめたこと：手元の試験用サーバーで、2 つの zip をまとめて送ると保存した場所・ラベル・保存リストが入り地点名が付くこと、zip でないファイルを断ること、画面の表示
- Takeout の zip は丸ごと残さず、使うファイルだけを取り出して `takeout/` の `saved/`・`labeled/`・`lists/` に置くようにした（写真などのほかのデータを持たないため）。zip に入っていた種類だけを置き換えるので、分かれた zip を別々に送っても前のデータが消えない。画面からもコマンド（import-takeout）からも同じ処理
- 確かめたこと：zip を 1 つ目だけ（ラベル・保存リスト）→ 2 つ目だけ（保存した場所）と別々に送って、どちらも残ること、まとめて送れること、コマンドで入れられること、Takeout でない zip を断ること。取り出したファイルは 2.7MB（zip は約 1.4MB。写真なしの書き出し）

## Takeout のクチコミとマイマップも拾う
- ユーザーの疑問：Takeout の説明にある「スター付きの場所」が zip に見当たらない。調べると、「マップ（マイプレイス）」の `保存した場所.json`（英語版は Saved Places.json）がそれで、すでに使っていた
- zip の中で使っていなかったもののうち、クチコミ（`クチコミ.json`。保存した場所と同じ形）とマイマップ（`マイマップ/*.kmz`。中の KML に地点の名前・座標）を拾うことにした（ユーザー：「拾えるものは拾いましょう。優先度は拾ってみないとわからない」）
- 作ったもの：取得方法 `takeout-review`（優先 25）と `takeout-mymap`（優先 35）。どちらも店・地点の側から、いちばん近い滞在先 1 か所にだけ付ける。マイマップは「保存リスト」のタブでも地図ごとに見られる（`mymap:地図の名前`）。保存リストの店の位置は、クチコミとマイマップの cid でも探す。マイマップの経路の線と位置のログ（名前が時刻だけの点）は除く
- 拾ってみた結果（手元の書き出し。タイムラインの地点 5,361 か所）
  - クチコミ 13 件 → 10 か所に付いた。ラベル・保存した場所のない地点は 1 か所だけ
  - マイマップ 12 個・1,555 地点 → 727 か所に付いた。うち 671 か所は `GoogleMaps_Backup_20180606a`（昔のスター付きのバックアップとみられる。cid 付き 1,424 件）。ラベル・保存した場所のない地点に付いたのは 170 か所（旅行の記録の地図など）。保存した場所と同じ地点で同じ名前が 243 か所
  - 保存リスト「行ってみたい」（3,458 店）で位置が分かる店が 18 → 53 に増えた（マイマップ・クチコミの cid から）。ほかのリストは変わらない
- 優先度は仮の値。見て決める

## 起動時のログに設定を出す
- サーバーで画面が更新されなかった。前の置き方から移した設定ファイルに `"publicDir": "./public"` が残っていて、古い画面を配っていた（ユーザーが確認して直した）。ログからは分からなかった
- ユーザーの方針：秘密の値以外はログに出しておく
- 起動時に、バージョン・Node.js の版・利用者の数と、全部の設定を 1 項目 1 行で出すようにした。秘密の値（項目名に secret / password / key / token / hash を含むもの）は「設定済み／未設定」だけ。設定ファイルに書いていない項目には「（既定）」、設定ファイルにあっても使っていない項目（古い passwordHash など）は知らせる。publicDir に index.html がなければ注意を出す

## 設置スクリプトと確認のコマンド
- サーバーで、新しいビルドをしても前の版のサーバーが動いていた。前の置き方の rc.d スクリプト（`${gtexp_dir}/server.mjs` を動かす）が残っていて、フォルダー直下の名残りの server.mjs を動かしていた。ほかにも publicDir・cron・持ち主など、一度だけの手作業でつまずいた
- ユーザーの方針：`sudo sh deploy/install.sh` でよい。名残りのファイルは、消さなくても正しく動くなら消さない
- 作ったもの
  - `deploy/install.sh`：Linux（systemd のユニットを、場所・ユーザー・node のパスを埋めて作る）と FreeBSD（rc.d と sysrc）。持ち主をそろえる、未ビルドならビルド、設定ファイルとログのフォルダーを用意、サービスを（再）起動、cron の fetch-osm の行が別の場所なら直す（`--osm-cron` でなければ入れる。ほかのユーザーにもあれば知らせる）、最後に check。何度実行してもよく、ファイルは消さない
  - `deploy/update.sh`：管理者で実行すると、更新・ビルドを持ち主で行ってから install.sh を続けて実行する
  - `node dist/server.mjs check`：Node.js の版、ビルドがソースより古くないか、設定ファイル、画面のファイル、書き込めるか、利用者、サービスの定義が今の dist/server.mjs を動かしているか、動いているサーバーが今のビルドか（`/api/health` で比べる）、cron、名残りのファイル（情報だけ）
  - 起動のログの行に、起動の日時とビルドの日時を出す
- 確かめたこと（手元）：check の表示、別のビルドで動いているサーバーを「要対応」と出すこと、スクリプトの文法（sh -n）。install.sh は Linux・FreeBSD の実機ではまだ動かしていない
- 動かすユーザー（gtexp）には sudo の権限を持たせない（ユーザーの指摘。持たせるとセキュリティ上の問題になる）。もともと install.sh / update.sh は sudo できる管理者のアカウントで実行する作りだったが、手順書やメッセージが gtexp で sudo するようにも読めたので、「管理者」と「動かすユーザー」の役割を手順書に表で書き、sudo のコマンドはスクリプトの絶対パス（`sudo sh /home/gtexp/gtexp/deploy/install.sh`）で示すようにした（gtexp のホームに管理者が cd できないこともあるため）。check と update.sh の案内も「管理者のアカウントで sudo sh <絶対パス>」にした
- サーバーで `sudo sh deploy/update.sh` を実行すると「gtexp@GORRY.NET's Password:」と聞かれた。スクリプトが root から `su -m gtexp` で動かすユーザーに切り替えるところで、FreeBSD の su の PAM の設定（Kerberos）が root からでもパスワードを聞いていた。切り替えは、認証をしない `sudo -H -u`（root からならパスワードを聞かない）を先に使い、なければ `runuser`（Linux）、どちらもなければ su を使うように直した

## 地図が出なくなった（デモ用のキーの上限）
- 「このページでは Google マップが正しく読み込まれませんでした」と出た。コンソールに `Maps Demo Key limit reached`。使っていた API キーが、請求先アカウントのないデモ用のキーで、1 日の上限に達した（確認のために何度も地図を開いたため。gtexp は画面を切り替えるたびに地図を読み込む）。gtexp の不具合ではない。設置手順の「6」に、デモ用のキーではなく通常のキーを使うよう書き足した
- 同じコンソールに出ていた警告（AdvancedMarker の 'gmp-click' を addListener で受けている）に合わせ、4 か所を addEventListener に直した
- API キーのウェブサイトの制限に gtexp のホスト名が入っていなかったときは `RefererNotAllowedMapError` になり、地図の場所には Google の短い案内しか出ず、続けてピンを作ろうとしてエラーが出ていた。Google が認証の失敗を知らせる `gm_authFailure` を受けて、地図の場所に「地図の API キーが使えない状態です（キーのウェブサイトの制限や課金の設定など…）。サーバーの管理者に連絡してください」と出し、地図を捨ててピンを作らないようにした（maps.ts。どの地図の画面にも効く。一度断られたら、読み込み直すまで地図は作らない）
- 確かめたこと：手元で gm_authFailure を呼び、開いていた画面と、あとから開いた画面の両方に案内が出ること（形式の正しくないキーでは Google は警告だけで認証の失敗まで進まなかったので、実際の断られ方では試せていない）
